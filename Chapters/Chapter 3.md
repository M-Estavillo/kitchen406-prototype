**CHAPTER 3**  
 **TECHNICAL BACKGROUND**

	This chapter presents the concepts, technologies, and tools relevant to the development of the proposed system. The discussion focuses on the foundational technologies that support modern web-based business systems.

**Frontend Technologies**

	Frontend technologies refer to the frameworks and tools used to create the user interface (UI) and user experience of a website or web application, which run directly on the client side within the user's browser (Kumar, 2025). In this system, the frontend will be built using Next.js, a full-stack framework based on React, which structures the user interface as a collection of reusable components rather than static pages. Through the App Router, Next.js distinguishes between Server Components and Client Components, allowing the system to decide where each part of the interface is rendered: server-side rendering (SSR) and static generation produce fully-formed pages that load quickly and are easier for search engines to index, while client-side rendering handles the dynamic, interactive elements that respond to user actions in real time. This hybrid rendering model ensures that pages achieve a fast initial load without sacrificing interactivity. Together, these technologies form the presentation layer of the application, translating raw data and business logic into an intuitive and responsive interface that end users can navigate with ease.

**Backend Architecture** 

	Backend architecture refers to the server-side structure of a web application, encompassing the logic, databases, and infrastructure that power its functionality behind the scenes (Gallardo, 2023). In this system, the backend is built within Next.js itself, which serves as a full-stack framework where the server-side logic resides in the same unified codebase as the frontend but remains architecturally distinct in responsibility. Rather than maintaining a separate server, the system uses Next.js Route Handlers and Server Actions to process incoming requests, execute business logic, and communicate with external services. Authentication and role-based access control (RBAC) are handled through Auth.js, which manages user sessions and restricts access to system features according to each user's assigned role, ensuring that only authorized personnel can perform sensitive operations. To bridge the application code and the database, the system employs Prisma as an object-relational mapper (ORM), allowing the backend to query and manipulate data through type-safe operations instead of raw SQL.

**Relational Database Management**

	A relational database management system (RDBMS) is a program used to create, update, and manage relational databases, which structure information into tables composed of rows and columns and establish links between data through common attributes (Google Cloud, 2024). In this system, PostgreSQL serves as the RDBMS, storing the application's structured data—such as users, products, components, orders, and transactions—in interrelated tables. Each table holds records as rows and attributes as columns, and relationships between tables are enforced through primary keys, which uniquely identify each record, and foreign keys, which reference records in other tables to link related data. This relational structure allows the system to model naturally connected information, such as associating an order with its customer and its constituent products, while normalization reduces data redundancy and preserves consistency across the database. To interact with PostgreSQL, the system uses Prisma as an object-relational mapper (ORM), which translates the application's object-oriented code into SQL operations, enabling the backend to perform type-safe queries without writing raw SQL directly. The database itself is hosted and managed on Railway, which provides the infrastructure for deployment, scaling, and maintenance.

**Bill of Materials (BoM) Structure** 

	A Bill of Materials (BoM) is a comprehensive list of the raw materials, components, and quantities required to manufacture a finished product, serving as the central record that links a product to everything consumed in producing it (Heinz, 2025). In the context of Kitchen406, the BoM takes the form of a recipe structure, where each product in the catalogue—such as a specific bread or pastry—is linked to the set of raw ingredients it requires and the exact quantity of each. This structure is modeled in the PostgreSQL database through a join table that connects the product table to the ingredient table, with each entry recording an ingredient and the quantity that product consumes, allowing a single product to reference many ingredients and a single ingredient to appear across many products. Because the bakery produces goods from raw materials rather than nested sub-assemblies, the BoM remains effectively single-level, mapping finished products directly to their constituent ingredients without intermediate components. This recipe-driven structure serves as the operational backbone of the system's inventory and pricing modules: when an order is confirmed, the system references the BoM to project and deduct the corresponding ingredient quantities from stock, enabling consumption to be forecast from confirmed orders rather than inspected visually, while the same ingredient quantities feed the cost-based pricing computation by aggregating the cost of each material a product consumes. In this way, the BoM connects the ordering, inventory, and pricing components into a single coherent chain grounded in each product's defined recipe.

**Cost-Based Pricing**

Cost-based pricing is a pricing strategy in which the selling price of a product is determined by first calculating the total cost of producing it and then adding a fixed markup percentage to arrive at the final price (Wall Street Prep, n.d.). In Kitchen406, this strategy is applied by computing each product's cost from the bottom up and then suggesting a price to guide the owners' pricing decisions. The system begins with the product's Bill of Materials, aggregating the cost of every raw ingredient in the recipe along with its packaging, which is treated as a direct material line rather than a separate expense. To this material cost, the system adds a per-product utility overhead value representing the gas and electricity attributable to the product; because true overhead cannot be calculated without reliable production-volume data, this value is not derived by the system but supplied by the owners, who set a general default that can be overridden for individual products whose baking demands differ, such as cakes that occupy the oven far longer than smaller items. The sum of ingredient cost, packaging, and utility overhead yields the product's total production cost, to which the system applies a single global markup percentage, also configured by the administrators, producing the suggested selling price. The resulting profit margin is then displayed back to the owners so they can evaluate the suggestion and adjust it against their own judgment before finalizing a price. Because the accuracy of this computation depends on the ingredient costs and overhead estimates the owners provide, the algorithm functions as a decision-support tool that grounds pricing in actual production cost rather than as an automated replacement for the owners' pricing authority.

**Capacity-Constrained Scheduling Logic** 

	Capacity-constrained scheduling refers to the logic of allocating incoming orders against finite production resources, where a business whose capacity is limited must decide which orders to accept and how to schedule those it accepts, since each order carries both revenue and a processing cost that must be weighed against the ability to fulfill it (Slotnick, 2011). In Kitchen406, this logic is implemented as a set of configurable capacity limits enforced at the point of booking, counted against the customer's chosen delivery date so that production is constrained by when goods are due rather than when they are ordered. The system maintains three independent limits, one for each purchasing workflow, so that standard orders, subscriptions, and custom cakes are counted separately and do not draw from a shared pool. For standard orders, capacity is enforced per delivery day, defaulting to a maximum of four product varieties per day with up to ten units of each variety; for subscriptions, capacity is enforced per week at a default of ten units per product, consumed week by week as each delivery in the four-week cycle approaches rather than reserved in full at enrollment, with the weekly delivery day fixed when the customer enrolls; and for custom cakes, capacity is limited to two per week, each of which must fall on a different delivery date. 

These baselines are not fixed in the system but are configurable by the administrators, allowing the owners to raise or lower each ceiling to match their fluctuating operational capacity. When a requested delivery date has reached the relevant limit, the system applies a hard block, refusing the booking for that date rather than waitlisting or silently overbooking it, which prevents the overcommitment that occurs when subscription and made-to-order production compete for the same baking days. This scheduling logic also operates in tandem with the inventory module, since a product whose required ingredients are depleted is disabled independently of its capacity slot, meaning an order can proceed only when both sufficient capacity and sufficient ingredient stock exist for the chosen date. The separation of capacity limits also applies when a product is offered through both standard ordering and subscription enrollment. A product's subscription preparation and delivery schedule governs its subscription commitments but does not automatically restrict the same product's availability for standard orders. Standard-order availability is evaluated against the customer's selected fulfillment date, considering the complete contents of the cart, applicable lead times and cut-off times, remaining standard-order capacity, blocked dates, and sufficient ingredient availability. All products included in a standard order must be available for fulfillment on the selected date before the transaction can proceed.

**Large Language Models (LLMs)** 

A large language model is a type of AI system trained on massive volumes of text and other content, allowing it to understand and generate natural language in response to a prompt (IBM, n.d.). In simple terms, it is the technology that lets a computer read a short instruction and write back a paragraph, or even an image, based on that instruction. In the proposed system, this technology powers the AI marketing assistant, which uses Google's Gemini model to generate both the caption and the accompanying image for Facebook posts describing the bakery's products, events, and subscription offerings. When a predefined business trigger occurs, the system automatically sends a prompt to Gemini containing relevant business information, and the model returns a caption and image pair that the owners can review and edit. The model is used only for this content generation. It plays no role in order processing, inventory calculations, or any other operational function of the system.

**Context-Grounded Generation**

Context-grounded generation is a way of feeding a language model current, specific facts right before it writes something, instead of letting it rely only on what it learned during training (Google Cloud, n.d.). In simple terms, it is like handing the AI a short, up-to-date fact sheet before asking it to write, so it does not have to guess or use old information. In the proposed system, this is done by pulling the bakery's own current data, such as which products are in stock and how many subscription slots are still open, then feeding it into the prompt every time a draft is made. Because this information is pulled fresh each time, a caption written for a product that has since sold out, or a subscription cycle that has since filled up, will reflect that instead of repeating outdated details. This also saves the owners effort because marketing posts are generated automatically when relevant triggers occur, reducing the need to manually create promotional content from scratch

**Human-in-the-Loop (HITL) Systems** 

Human-in-the-loop means a person stays involved in reviewing or approving what an automated system produces, rather than letting the system act entirely on its own (IBM, n.d.). The key idea is that the AI never gets the final say. A human always checks its work first. In the proposed system, this is how every one of the drafts is handled. A generated image and caption is never posted by itself. It goes into an approval list on the admin dashboard that only the owners can see. From there, the owners can edit it and choose when it should be posted. Nothing written by the AI ever reaches Facebook on its own. The owner manually posts generated content to the facebook page. This keeps the final decision over what is said about the bakery, its products, and its prices in the owners' hands, and gives them a chance to catch anything wrong or outdated before it goes public.

**Role-Based Access Control (RBAC)**

Role-based access control is a way of giving people access to only the parts of a system their role requires, instead of giving everyone the same access (National Institute of Standards and Technology \[NIST\], n.d.). It is like giving an employee a key that only opens the rooms they need to work in, not every room in the building. In the proposed system, this principle is applied on both the customer side and the staff side. On the customer side, the platform distinguishes between guests and logged-in users. A guest, meaning anyone browsing without an account, can still view products, explore subscription options, and browse information about the bakery. However, placing a standard order, submitting a custom cake request, or subscribing to a product requires a registered account. Requiring customers to log in allows the system to associate orders, payments, delivery information, and subscription records with a specific customer profile. It also enables customers to track their orders, manage their subscriptions, and access their transaction history through a single account. On the staff side, RBAC separates what future hired staff can see and do from what the owners can. Staff accounts can manage orders and inventory only, since these are the tasks they are hired to handle, while owner accounts are the only ones that can see sales figures, customer information, profit details, and the AI marketing draft posts. A staff account simply cannot open these restricted areas, even if they know they exist, which lets the owners hand off daily order and inventory work to hired help without exposing money or customer details the way an open whiteboard or spreadsheet would.

**Application Programming Interfaces (APIs)**

An application programming interface, or API, is a set way for one computer program to ask another program for information or to perform an action (IBM, n.d.). It works like a waiter taking an order to the kitchen and bringing the food back. The system asks another company's system for something, and that system sends a response back. In the proposed system, APIs are used to connect the platform to outside services rather than building that functionality from scratch: PayMongo for processing payments, Lalamove for delivery quotations and tracking, Brevo and Semaphore for sending notifications, and Google Maps for location-based features.

**Payment Gateway Integration**

A payment gateway is an online service that securely handles a payment between a customer and a business, checking that the payment goes through before the order is treated as confirmed (Zuora, n.d.). Simply, it is the middleman that takes the customer's payment and tells the business, "this has been paid." In the proposed system, this role is filled by PayMongo, a Philippine payment gateway that lets businesses accept payments through cards and e-wallets via a single API rather than dealing with individual banks directly (PayMongo, n.d.). One of the payment methods PayMongo supports is QR Ph, the national standard QR-based payment system set up by the Bangko Sentral ng Pilipinas so that payments can move between different banks and e-wallets using one common type of QR code (Bangko Sentral ng Pilipinas, n.d.). 

No order is considered confirmed until it has passed through PayMongo. This applies to standard orders, prepaid subscriptions, and finalized custom cake quotations alike. At checkout, the system generates a PayMongo payment request for whatever the customer owes, whether that is a single order, a subscription, or an agreed cake quotation, and the customer completes that payment through PayMongo's supported methods, which includes QR Ph. Once the customer pays, PayMongo tells the system the payment went through, and the system marks the order as paid and moves it into production planning. For subscriptions, this is also the point where the four-week delivery schedule officially begins. This ensures the owners never commit baking time and ingredients to an order that hasn't actually been paid for.

**Google Maps Platform**

	It provides a collection of APIs that let a developer show maps, look up places, and calculate routes. Three of these are used in the system: the Maps JavaScript API, which is used to build and display an interactive map directly on a web page and lets locations be shown, along with custom markers and interactive data layers; the Places API, which provides place details, search, and autocomplete for looking up and validating specific addresses or establishments; and the Routes API, which is used to calculate distance between two locations. In the proposed system, these services support the delivery side of the platform by allowing customers to search for, validate, and save delivery addresses through an autocomplete field, assign labels to saved addresses, and designate a default delivery address within their account. Customers can also select a saved address during checkout and visually confirm it on an interactive map before submitting an order. The Routes API is used to calculate the route and distance between the bakery and the selected delivery address to verify that it falls within the bakery’s serviceable area. This works alongside the Lalamove integration, which handles the actual booking and tracking of deliveries, while Google Maps Platform manages the location, address validation, and distance verification processes.

**Notification Systems**

Sending customers timely updates is handled through two outside notification services rather than being built directly into the system. Brevo is a platform that provides an API for sending transactional and marketing emails, along with SMS and other messaging channels, used by businesses to handle their outgoing customer communications. Semaphore is a Philippine SMS gateway API that lets a business send text messages to mobile numbers on all major local networks, including Smart, Globe, and Sun (AgentiaSystems, n.d.). In the proposed system, Brevo is used to send email notifications, such as order confirmations or subscription reminders, while Semaphore is used to send SMS text messages, which is useful for customers who may not check email as often as their phone. These services are triggered automatically at key points, such as when an order is confirmed, when a delivery status changes, or when a subscription delivery is coming up, so the owners do not have to manually message every customer with the same routine updates the way they currently do through Facebook Messenger.

**Logistics Provider API**

A logistics provider API is a service that lets an application request delivery-related actions, such as price quotes and order tracking, directly from a courier company's system (Lalamove, n.d.). In the proposed system, the Lalamove API is used at two points in the standard-order workflow. First, during customer checkout, the system calls the API to retrieve a delivery quotation so the customer sees the delivery fee before paying. The customer's address details are then stored, but the actual delivery is not booked yet. Once the order is ready, the owner manually triggers the booking from the admin side using those stored details. After a booking is placed, the system tracks the delivery's progress through webhooks, which are automatic status messages Lalamove sends to the system each time an order's delivery status changes, allowing the customer to follow their order's status without the owner having to relay updates by message. The system does not display a live map of the driver's route. It only reflects the status updates Lalamove’s webhooks provide. 

**Hosting Infrastructure**

Hosting infrastructure refers to the servers and online platforms that make an application available on the internet so that users can access it through a web browser (Vercel, n.d.). The proposed system runs across two hosting platforms, each handling the part of the system it is best suited for. The main application, built as a full-stack Next.js project that covers both the customer-facing website and the business logic behind it, is hosted on Vercel, a platform designed for delivering fast, publicly accessible web applications (Vercel, n.d.). The system's data, including products, orders, and customer details, is stored in a PostgreSQL database hosted on Railway, a cloud platform that runs the database and other supporting background processes (Railway, n.d.). The application communicates with this database through Prisma, a tool that lets the system read and write data in an organized and consistent way (Prisma, n.d.). Separating the public application from the database in this manner keeps the running website and the stored data independently managed, which makes the overall system easier to maintain and update. 

**Authentication & Session Management**

Authentication is the process of confirming that users are who they claim to be, typically by having them prove their identity with credentials such as an email and password, while session management is what keeps a user recognized as logged in as they move through the application (Auth.js, n.d.). In the proposed system, authentication is handled using Auth.js, a library built for Next.js applications that manages user registration, login, and session handling in one place. When a customer registers, they must confirm their account through an email verification step before it becomes active, which helps ensure that accounts are tied to real, reachable email addresses. Passwords are never stored as plain text. They are converted into a hash so that the actual password is never kept on file. Once a user successfully logs in, the system keeps them recognized as logged in across their visit and attaches the user's assigned role, whether customer, owner, or staff, so that the system knows not only who the user is but what they are permitted to access, which supports the role-based restrictions applied elsewhere in the system. 

**Asynchronous Task Processing**

Asynchronous task processing refers to work that a system carries out on its own in the background, on a set schedule, without a user having to start it each time (Railway, n.d.). In the proposed system, this is handled through a cron job, which is a task set to run automatically at fixed times or intervals rather than in response to a user's action. The cron job is configured and run on Railway, the same platform hosting the system's database, which triggers the task on a defined weekly schedule without anyone needing to be online or to press anything for it to start. When the scheduled time arrives, the job automatically runs the routine that generates a social media post draft based on the system's own data, after which the draft is stored for the owner to handle separately. Using a scheduled background job for this means the work happens reliably on its own at the set time, independent of whatever the owners are doing, so a recurring task that would otherwise be easy to forget is carried out consistently without occupying their attention.

**File Image Storage**

File image storage refers to the use of a dedicated cloud service to hold and deliver a system's image files, rather than keeping those files on the system's own server or database (Cloudinary, n.d.). In the proposed system, Cloudinary is used to store three kinds of images: product photos, custom request reference pictures, uploaded product review photos, and generated marketing images. In both cases, the image first passes through the system's backend, which then sends it to Cloudinary for storage. Rather than keeping the image files themselves, the system's database only stores the link pointing to each image in Cloudinary, which is retrieved whenever the image needs to be displayed. Handling images this way keeps the database lightweight and focused on the system's core data, while the storage and delivery of the actual image files are managed by a service built specifically for that purpose.
